# Mining Companion: equipment data for Star Citizen 4.10.3 LIVE and where to get it

## 0. Scope, method and patch status

- **Current LIVE patch: 4.10.3-LIVE.13165946.** It went live on 12 Nov 2026.
  - Verified: the scunpacked-data repo's commits are named after the game build. Its latest commit (`3cc8072`, 2026-11-21) is "4.10.3-LIVE.13165946".
  - Bedrock 3.0.5 (commit `e5c96ac`, 2026-11-22) says in its README that it is "for Star Citizen 4.10.3".
  - Sources: https://github.com/StarCitizenWiki/scunpacked-data, https://github.com/SC-Ravaxx/Bedrock, and the 4.10.3 news at theimpound.com and starcitizen.tools (seen only as search summaries).
  - Confidence: **high**.
- **5.0 is on PTU.** Bedrock's `include/MiningAdvice.h` says Nyx I rocks in "5.0, PTU build 13189690" use `miningglobalparamsship_v5.xml`, with `decayPerMass 1.45` (instead of 0.2) and `cSCUPerVolume 7.61` (instead of 0.7).
  - The data pipeline therefore has to be version-aware.
  - Confidence: **medium** (the Bedrock author measured this on PTU; I did not check the 5.0 files myself).
- **Reference tool "Bedrock" is open source.**
  - Repo: https://github.com/SC-Ravaxx/Bedrock, GPL-3.0, C++, Windows and Linux.
  - Its equipment table `include/MiningHardware.h` is generated by `gen_mining_hardware.py` straight from the game's `Data.p4k`. That is reading files on disk, not process memory, so it is compatible with anti-cheat.
  - Confidence: **high**.
- **Network limits in this session.** These hosts could not be reached here: starcitizen.tools, api.star-citizen.wiki, uexcorp.space, api.uexcorp.space, regolith.rocks, erkul.games, robertsspaceindustries.com, the-forsaken.org.
  - What I say about those sites comes from web-search summaries and is marked **medium/low**.
  - Everything else was verified on GitHub. I cloned three sources and parsed the JSON and code myself: scunpacked-data at 4.10.3, Bedrock at its latest commit, and RegolithCo-Common plus mort13/BreakabilityChart.

## 2. Laser heads, 4.10.3 LIVE

Source: scunpacked-data `items/mining_laser_*.json`, cross-checked field by field against Bedrock `MiningHardware.h`. All values agree.

Field origins (raw = game DataCore XML):
- **Max power** = `DamageEnergy` of the `SWeaponActionFireBeamParams` with `hitType="ElectricArc"`. In scunpacked this is `stdItem.MiningLaser.PowerTransfer`.
- **Min throttle** = `SEntityComponentMiningLaserParams.throttleMinimum`. Min power = PowerTransfer x throttleMinimum (scunpacked `MinPowerTransfer`).
- **Extraction** = beam with `hitType="Extraction"`.
- **Ranges** = `fullDamageRange` / `zeroDamageRange` (shown in the game as Optimal / Maximum range).
- **Modifiers** = `miningLaserModifiers.{optimalChargeWindowSizeModifier, optimalChargeWindowRateModifier, resistanceModifier, laserInstability}.FloatModifierMultiplicative.value`.
- **Inert filter** = `filterParams.filterModifier`.
- **Module slots** = number of `BONE_ItemPort_Consumable_n` ports.

Modifiers are percentages. Confidence: **high**.

**What this means for the calculator:**
- **Laser stats have no catastrophic charge rate modifier and no shatter-damage modifier in 4.10.3.** I checked the raw `miningLaserModifiers` of every head; only window size, window rate, resistance and laserInstability exist. Those two stats come only from modules. Confidence: **high**.
- **Range.** Bedrock assumes full power up to `fullRange`, zero at `zeroRange`, and a straight line in between. Bedrock itself says the shape of that falloff is not in the game files. Confidence: **medium**.

**Patch history: power changed in 4.9.0, and the in-game descriptions were never updated.** Verified by diffing scunpacked-data commits 4.8.3-LIVE.12122953 (`c431f16`) and 4.9.0-LIVE.12232306 (`acaf6c7`):

- The 4.9 patch notes say ship mining laser power rose "by about 20 % across the board" (starcitizen.tools/4.9 via search, **medium**). The data change itself is **high** confidence.
- **The item description text still shows the old 4.8 numbers.** For example, Helix II `DescriptionData["Mining Laser Power"] = "1020 - 4080"`. Anything built by scraping descriptions is therefore wrong by about 20 %, and UEX's item attributes are one such source (see §4).
- Nothing changed between 4.8.3 and 4.10.3 in any module or gadget value, or in any laser modifier or slot count. The only differences are four new items: Clearcut, Deluge, Overrun and the Hyūn head, all added in 4.10.0-LIVE.12519617. Confidence: **high**.

## 3. Modules and gadgets, 4.10.3 LIVE

Source: scunpacked-data **Raw** blocks, which match Bedrock exactly. Raw paths:
- Charges and stacking: `Raw.Entity.Components.EntityComponentAttachableModifierParams.{charges, canInterrupt, isInterruptible, activationMethod}`.
- Power factors: `…modifiers[i].weaponModifier.weaponStats.damageMultiplier`, where **`fireActionIndex` 0 = fracture beam (ElectricArc)** and **1 = extraction beam**.
- Duration: `…modifiers[i].modifierLifetime.ItemModifierTimedLife.lifetime`.
- Module percentages: `…modifiers.ItemMiningModifierParams.MiningLaserModifier.{laserInstability, resistanceModifier, optimalChargeWindowSizeModifier, optimalChargeWindowRateModifier, shatterdamageModifier, catastrophicChargeWindowRateModifier, filterModifier}`.
- Gadget percentages: `…modifiers.ItemMineableRockModifierParams.MiningLaserModifier.{laserInstability, resistanceModifier, clusterFactorModifier, optimalChargeWindowSizeModifier, optimalChargeWindowRateModifier}`.

Power is a plain factor (1.25 = +25 %); everything else is a percentage. Confidence: **high**.

**Stacking flags (high confidence, from data):**
- **Surge** has `canInterrupt=0, isInterruptible=0`.
- **Every other active** has `canInterrupt=1, isInterruptible=1`.

What Bedrock infers from those flags (**medium**):
- Only one interrupting active runs at a time, and a second copy only replaces the first.
- Surge and all passives run alongside everything, including a second Surge.

### 3c. Gadgets (attach to the rock, one per rock, no charges)

| Gadget | Instability % | Window % | Charge rate % | Resistance % | Cluster factor % |
|---|---|---|---|---|---|
| BoreMax | -70 | 0 | 0 | +10 | +30 |
| Okunis | 0 | +50 | +100 | 0 | -20 |
| OptiMax | 0 | -30 | 0 | **-25** (description text says -30; the record is -25) | +60 |
| Sabir | +15 | +50 | 0 | -50 | 0 |
| Stalwart | -35 | -30 | +50 | 0 | +30 |
| Waveshift | -35 | +100 | -30 | 0 | 0 |

- **Cluster factor is how much ore survives the break, not how the rock splits.** This is Bedrock's reading of the gadget descriptions (**medium**).
- **Gadgets scale the rock's own figures multiplicatively:** `rock.instability x (1 + g/100)` and `rock.resistance x (1 + g/100)` (Bedrock `withGadget`).
  - This matches the user's Bedrock screenshot: BoreMax takes "Instability 64.2 -> 19.2", and 64.16 x 0.30 = 19.25. Confidence: **high** for the arithmetic.
- **Once a gadget is on, the scan panel already shows the gadget-modified values.** For example, 56 % reads 28 % under a Sabir. Divide back before applying the gadget yourself (Bedrock `withoutGadget`). Confidence: **medium**.

### 3d. How the stats combine (the conflict matters for the calculator)

- **Bedrock (4.10.3) multiplies every module:** `power = base x Π(module power)`, `window = 100 x (1+laser/100) x Π(1+module/100)`, and so on. Instability is added up, not multiplied. The crafting bonus is applied last.
  - Bedrock's evidence is a HUD screenshot: Helix I + Focus III + Rieger-C3 prints FRACTURE PWR 119 (= 100 x 0.95 x 1.25) and WINDOW SIZE 83 (= 100 x 0.60 x 1.40 x 0.99).
  - Additive stacking would give 120 and 99, so the window value clearly separates the two models.
  - Confidence: **medium-high**.
- **Regolith (`src/loadoutCalc.ts`, comment dated Feb 2025 / 4.0.1) adds them:** `1 + Σ(m_i - 1)`, "As of 4.0.1 modules stack again".
  - This is older and contradicted by the 4.10 HUD check. Treat it as outdated. Confidence that it is outdated: **medium**.
- **Resistance and break formula** (summarized here only to show the equipment data is consistent; another topic owns the details):
  - Bedrock: `P_eff = P x (1 - (R_rock x M_head)^1.21)` and `required = 0.2 x mass` per second (decayPerMass 0.2). The exponent 1.21 is Bedrock's own fit to measured rocks.
  - mort13 uses the linear `P x (1 - R x M)`.
  - My cross-check (inferred): the user's example rock (4,627 kg, RES 56 %) with a stock Hofstede-S2 gives 4060 x (1 - (0.56 x 0.70)^1.21) = 2752 W against 925 needed, which is **33.6 %**. That matches Bedrock's "30-38 %" for the middle Hofstede-S2. So the table values above reproduce Bedrock's output.

**scunpacked parsed-view bugs.** Use the `Raw` sections, not `Item.stdItem`. Verified by comparing against the raw blocks:
1. `stdItem.MiningLaser.Modifiers.AllChargeRates` simply repeats the inert filter value (Helix II shows 40). The raw laser has **no** charge-rate modifier, so this field is wrong.
2. `stdItem.MiningModule.Modifiers.DamageMultiplier` mixes `fireActionIndex` 0 and 1:
   - FLTR-XL shows 0.95 and Vaux-C3 shows 1.25, but those are **extraction**-beam factors.
   - Forel shows 1.5; that is also extraction.
   - Deluge's, Clearcut's and Overrun's fracture factors (1.15 / 1.15 / 1.02) are missing.
3. `DescriptionData` and `Description` strings show pre-4.9 power values.

**Recommendation for Node/TypeScript:**
- Write a build-time or server-side script that fetches the roughly 50 relevant JSON files from raw.githubusercontent.com, pinned to a commit SHA, and records the build string from the commit message (e.g. `4.10.3-LIVE.13165946`).
- Extract only the Raw fields listed in §2/§3 and §1 into your own `mining-equipment.<build>.json`.
- Add a unit test that compares the result against Bedrock's `MiningHardware.h` values (the tables above).
- Pull prices and shops from UEX separately, with your own app token.
- Check GitHub for a new commit (`GET https://api.github.com/repos/StarCitizenWiki/scunpacked-data/commits/master`) and rebuild when the message names a new build.
- Suggested model:
  - `Laser {id, name, size, power, throttleMin, extraction, rangeFull, rangeZero, mods:{window, rate, resistance, instability, filter}, slots, requiredTags[]}`
  - `Module {id, name, active, power, extractionFactor, mods:{window, rate, resistance, instability, filter, shatter, catastrophic}, uses, durationS, canInterrupt, isInterruptible, craftOnly}`
  - `Gadget {id, name, mods:{instability, window, rate, resistance, cluster}}`
  - `Ship {id, heads:[{port, size, stockLaser, fixed}], oreScu}`
  - Plus a per-head `craftedPowerPct` the user types in.

## 5. Verified vs. inferred

- **Verified in primary data** (scunpacked 4.10.3 Raw JSON and Bedrock source code):
  - every number in the laser, module and gadget tables;
  - slot counts, size restrictions and required tags;
  - the 4.9 power jump (diff of two commits);
  - the stale descriptions;
  - the four items added in 4.10.0;
  - pod capacities;
  - scunpacked's parser bugs;
  - the staleness of Regolith's data.
- **From Bedrock's in-game measurements** (an informed third party): multiplicative stacking, the Surge stacking behaviour, the resistance exponent 1.21, the straight-line range falloff, the crafting range of 0.64x to 1.44x, and the 5.0 PTU v5 rock parameters.
- **From web-search summaries only** (hosts unreachable here):
  - 4.10.3 release date;
  - the 4.9 patch-note wording;
  - Hyūn release status;
  - UEX quota and token terms;
  - wiki API terms;
  - Erkul having no public API.
- **Inferred by me:**
  - The 33.6 % check against the Bedrock example rock.
  - UEX's mining stats are probably still the pre-4.9 values. I saw this only in mort13's snapshot, not in a live API call.
